# 使用情境：在明確約束下搜尋更好的策略

[繁體中文首頁](README.zh-TW.md) · [English guide](use-cases.md) · [英文任務模板](task-brief.md) · [模型證據](step-evidence.zh-TW.md)

Step Engineer 要強化的使用方式是：**由主 Agent 定義環境、目標與允許的取捨，讓 Step 透過執行回饋，在可行範圍內搜尋更好的實作與策略。** 這是專長假設；目前的展示與本地案例尚不能證明它在所有約束任務中領先。

「邊界解」指善用合法餘裕的方案，例如用部分召回率換取速度。接近門檻只有在提高目標、且能通過驗收時才有價值；品質更高也可能是產品所需，不能擅自認定是浪費。

## 先判斷是否值得委派

任務需要能回答以下六項；答案應落在任務契約與可執行評估中。

| 項目 | 要定義的內容 | 資源配置範例 |
| --- | --- | --- |
| 環境 | 輸入範圍、容量、可觀察狀態、固定假設 | 一批工作及 CPU／記憶體的整數容量 |
| 可調動作 | 哪些策略、參數或程式可改 | 選擇工作組合，只改 `policy.py` |
| 目標 | 一個主要分數、單位、方向、跨情境彙總方式 | 最大化受測工作組合的收益 |
| 硬限制 | 任何一次都不能違反的條件 | 不超容量、合法且不重複的工作 ID、不改輸入 |
| 允許的取捨 | 為了主目標可以犧牲什麼，以及犧牲到哪裡 | 可以少接工作；單件價值最高不一定使總收益最高 |
| 最終驗證 | 未參與調校的情境、門檻、拒絕條件 | 新 seeds／容量組合，逐情境驗限制並檢查保留集收益 |

此外，先建立**合格 baseline**，讓模型有可比較的起點。若已有成熟演算法或 solver 可直接解決，先使用或比較它；有約束不代表一定要花費模型預算。資源配置範例是任務契約示範，未主張優於動態規劃或最佳化求解器。

以下情況先由主 Agent 釐清：需求模糊、只憑主觀喜好評分、沒有可執行環境、無法保護評估器，或 baseline 已違反硬限制。現有 harness 遇到不合格 baseline 會停止，不會自動修復需求。

## 四類具體情境

| 情境 | 可探索的策略 | 目標與不可違反的條件 | 需要的驗證與目前狀態 |
| --- | --- | --- | --- |
| 資源配置 | 排序、選擇組合、搜尋演算法 | 提高總收益；同時守住 CPU 與記憶體容量 | [可執行合成範例](../examples/resource_allocation/README.md)。保留集改變輸入與容量；尚未進行本例的付費 Step 試跑 |
| 搜尋／索引調校 | 分桶、量化、探查範圍、重排候選數 | 提高吞吐量；召回率及記憶體守住事前門檻 | 須提供工作負載、精確答案與新查詢資料；本 repo 未附向量索引評測器 |
| 離線排程／配送策略 | 批次、順序、路徑、合法寬限的使用 | 提高收益或吞吐；守住容量、衝突與服務條件 | 須提供模擬器，測試不同需求密度與隨機情境；本 repo 未提供交通／配送控制器 |
| 精確行為的效能優化 | 資料結構、快取、向量化、重用中間結果 | 降低耗時；保持精確輸出、資料不變性等契約 | 有[批次聚合示範](../examples/batch_aggregation/README.md)及[一個圖像合成實測](case-study.md)；新工作負載仍需自己的檢查 |

前三類的價值在於探索允許的取捨；第四類則保留行為，只探索實作空間。
目前所有任務都透過**本機程式或策略檔的修改**表達。模擬器與評估命令由呼叫端提供；Step 不直接控制真實路口、車隊或生產資源。

## 目標有張力，與限制真正矛盾

- **可優化的取捨**：CPU 密集與記憶體密集的工作爭用不同資源，可以換組合；速度與召回率互相拉扯，可以在已核准的門檻內調參。
- **真正無解**：同一量同時要求小於等於 10、且大於等於 12。應交回需求擁有者處理；不能讓 Step 偷改限制或評分方式。現有 schema 不會自動證明所有領域條件是否可同時滿足。
- **未定義的產品成本**：評分器沒有扣延遲，不代表使用者不在乎延遲。先把需求轉成硬限制、事先固定的分數或驗收條件，再探索。

若要利用寬限、犧牲部分品質或增加記憶體，必須先寫明允許範圍。若有噪音或資料漂移，主 Agent 可以設定比產品底線更保守的作業門檻；裕度由需求與量測決定，不能跑完再任意降低。

## 可複製的委派格式

以下是主 Agent 的規劃模板，不是新增的 JSON schema。

```text
任務：
環境與適用範圍：輸入型別／大小、容量、負載、固定假設。
可調動作：可改的檔案、參數、策略；允許哪些實作自由度。
主要目標：分數、單位、方向、彙總規則、最低改善量。
硬限制：逐情境門檻、等號是否允許、如何量測。
允許的取捨：可降低哪些次要指標；明確底線與必要裕度。
合格 baseline：版本、分數、限制量測與檢查結果。
開發回饋：分數、資源使用、違反條件的原因。
保留情境：新的 seeds／輸入／負載；硬限制與成果驗收條件。
預算：時間、請求、工具、tokens、估算費用、無改善次數。
交付：已驗收 patch、量測／限制證據、停止原因及適用界線。
```

對應既有 `JobSpec`：

| 契約內容 | 現有實作 |
| --- | --- |
| 環境、動作與允許取捨 | `objective` 說明；`files`／`editable_files` 限制修改範圍 |
| 固定評估器 | 保護 `checks`／`benchmark` 使用的程式，排除於 `editable_files` |
| 主要分數 | `metric`／`direction`；`minimum_relative_improvement` 控制最低改善量 |
| 數值硬限制 | `constraints`，每次 benchmark repetition 都要成立；領域內逐情境檢查由評估器實作 |
| 量測與回饋 | `benchmark` 輸出可信任的 metrics；`repetitions` 使用中位數，不代表泛化測試 |
| 保留情境 | `final_only_files` 隱藏開發期檔案；`final_checks` 必須自行判斷保留情境分數與限制，失敗時回傳非零 exit code |
| 停止 | `budget`；耗盡探索時間後嘗試驗收已保存的最佳候選 |

`final_checks` 的輸出不會自動套用 `constraints`。僅列出保留集的分數、不在檢查程式中拒絕違規，不能建立驗收保障。`final_only_files` 對開發工具隱藏，但在最後執行時被測程式仍可讀到，不能當成對惡意程式的隔離。

## 主 Agent、Step 與 harness 各自負責什麼

- **主 Agent**：保留使用者選定的模型與推理設定（例如 Ultra），決定任務是否適合、定義規則與評估、比較 baseline／既有 solver、設定預算、審查最終成果並決定採用。
- **Step**：在允許範圍內選策略、修改實作、請求量測，根據觀察到的回饋繼續探索。
- **Harness**：保存工作副本、派送固定工具、執行檢查、限制預算、保存最佳可行版本並做最終驗證。它不替產品擁有者定義「什麼值得最大化」。

目前一次 job 只有一個主要分數，不會自動產生 Pareto 前緣、最佳性證明或無解證明。跨 job 的經驗檢索與自動策略摘要也尚未實作。

## 怎麼證明這個定位有用

先用範例驗證契約與執行流程，再用獨立評測比較策略。固定模型、推理設定、工具、規則與預算，保留簡單 heuristic／成熟 solver 的結果，對多個代表性任務重複試跑。

比較已驗收比例、保留情境的目標改善、硬限制違反、首個合格改善的時間與成本；所有失敗、中斷及未產生 patch 的試跑也要計入。貼近門檻的程度可以幫助診斷，但不應單獨當作成功指標。跨任務／版本比較由 runtime 外部的評測工具負責；harness 記錄每次工作的驗證與證據。
