# 測試篩選：保留故障辨識能力，減少無效執行

[English rules](test-selection.md) · [貢獻指南](../CONTRIBUTING.md)

這份規則用於專案開發期間的測試審查與選測。**目標是減少沒有增加證據的執行成本，而不是減少測例數。** Step 可提出篩選或降層方案；主 Agent 定義不可修改的契約、驗收並審查採用。

一般優化 job 的 `checks`、`benchmark`、`final_checks` 仍由主 Agent 固定，不能讓受測候選自行省略對自己不利的檢查。若任務本身是優化測試，必須另設不可修改的驗收器來檢查測試品質。

## 五種判定

| 判定 | 適用條件 | 需要的證據 |
| --- | --- | --- |
| 保留 | 有獨特契約、輸入類別、狀態、故障或外部觀測 | 指出它保護什麼，以及其他測試缺少什麼 |
| 降低執行層級 | 純解析／計算案例反覆建立昂貴的外部環境 | 保留原輸入及預期結果；另有真實整合錨點證明程式確實接到執行路徑 |
| 本次暫不執行 | 修改不會影響該契約與其依賴，且沒有新疑慮 | 明確修改範圍、共享依賴與重新納入的條件；不永久刪除 |
| 合併或刪除 | 保留者能替代被移除者的全部有效觀測 | 列出替代 test ID、同輸入類別／狀態／契約的對應，及固定故障檢測結果 |
| 不確定，保留 | 缺少等價性、依賴或執行證據 | 記錄未知原因，不能把未知當成冗餘 |

## 不可只靠這些理由刪除

- 名稱相似、行覆蓋率相同、同樣回傳 pass、一直沒有失敗。
- 參數案例多、執行慢、看起來只測一行程式。
- 單元測試已通過，所以推論 sandbox、Git、MCP 或程序清理一定有效。
- 一個總分／平均值相同，所以忽略個別情境的限制違反。

例如 development gate 與 final gate 都拒絕某候選，不代表只需一個測例：移除其中一個 gate 時，只有把另一階段設為可通過的案例，才能檢出缺陷。Timeout 與 cancellation 也不是同一個程序生命週期。

## 必須保留的區別

1. **允許與拒絕**：guard 不能因為全部拒絕而通過；等於門檻、略低、略高各有明確語意。
2. **不同狀態與方向**：baseline／探索／最終驗證、minimize／maximize、counter reset、同批／跨批工具、已退出主程序但仍有子程序。
3. **故障與恢復**：錯誤、取消、逾時、無效資料、預算耗盡、失敗後仍保存或驗收已知最佳版本。
4. **真正的外部觀測**：作業系統隔離、網路拒絕、pipe 排空、程序群組清理、Git index 與 working tree 差異、MCP stdio。
5. **跨控制互動**：個別門檻都對，不代表「停止探索後仍驗收精確達標的 saved best」一定成立。
6. **數值與資料類別**：零／負值／極端尺度、空輸入、型別變更、合法與非法 ID，不能只保留一般正值。

這些是需要覆蓋的契約維度，不是要求為每個標籤另造一個測試。既有案例若已提供觀測，可以直接引用。

## 執行步驟

1. 固定版本、測試清單、工具鏈與量測方式。先確認 baseline 通過；原本失敗不能透過刪測試變綠。
2. 列出候選 test ID／參數案例、保護的契約、觀測層與耗時。優先找可節省的重複 setup／I/O，避免在極便宜的數值測試上花更多篩選成本。
3. 對每個提案指派上述五種判定。涉及合併／刪除時必須列出存留的替代案例；不確定就保留。
4. 固定驗收條件後才交給 Step。可限制為只改指定測試函式，保留全部 node ID／參數與關鍵整合函式，讓 Step 搜尋較便宜的測試寫法。
5. 用原版與候選測試檢查同一組刻意注入的故障。原版可檢出的每個相關故障，候選或指定的保留案例都必須繼續檢出：`kills(old) ⊆ kills(retained witnesses)`，不能用新增檢出抵銷漏失。只有預期測例的 assertion 檢出故障才算有效；import error、collection error、timeout、skip 或崩潰不能算成功檢出。
6. 對同一版本的 baseline／候選交錯量測，報告命令、重複次數、時間範圍與中位數。故障集合只支持其涵蓋的缺陷，不證明所有未來缺陷都不漏。
7. 主 Agent 審查 diff、測試契約及實際流程，再跑相關測試與最終完整 CI。全部通過才採用。

不得為了變快新增 skip／xfail、降低門檻、改預期結果、減少必要 repetition、辨識測試名稱後硬編答案、改受測 production code，或把失敗改成成功。若發現產品契約已改變，應另開契約修訂，不能混在測試最佳化裡。

## 開發中如何避免重跑無關測試

以下是人工／主 Agent 選測指引，不是自動依賴分析器。需要核對實際修改；同一獨立契約內的多項修改取聯集，跨 guard、共用 helper／fixture 或影響不明確時全跑。

| 修改範圍 | 本輪先跑 |
| --- | --- |
| 純文件，未動程式、可執行範例或配置 | 本地連結／範例指令檢查及公開檔案 audit；不因文字微調重跑全部 pytest |
| `examples/resource_allocation/` | `tests/test_resource_allocation.py`，包含兩個真 sandbox 流程 |
| `tools/check_public_tree.py` 或其測試 | `tests/test_public_tree.py` 加實際 repository 的公開檔案 audit |
| 改善率門檻 | 完整數值群、一般 harness 接受／拒絕與 golden integration；不能只挑會通過的門檻 |
| deadline／stagnation | 相應狀態測試、停止後驗收、golden integration；同批與跨批都要考慮 |
| `tests/test_harness.py` 的共用 helper | 完整測試；reserve、stagnation、golden integration 直接 import helper，不能只依修改檔名選測 |
| 共用 runtime／workspace／models、平台、依賴、CI、打包或未知範圍 | 完整測試；局部選測規則不作為豁免 |

同一程式、測試、依賴與環境狀態下已有通過結果，且沒有新改動、失敗或未解疑慮，就不為了「再確認一次」重跑。若有新證據使先前結果不再適用，重新驗證相關部分。CI 仍保留完整 suite，作為局部迭代後的整合驗收。

## Step 的交付格式

每個提案至少包含：

```text
測試／參數 ID：
判定：保留／降層／本次暫不執行／合併刪除／不確定保留
契約與故障：
輸入類別、狀態、觀測層：
保留的替代案例或整合錨點：
允許修改與不可修改範圍：
原版／候選的故障檢測結果：
原版／候選的耗時與量測命令：
尚未驗證的風險與必須重新納入的條件：
```

主 Agent 應拒絕只有「重複」「太慢」「coverage 沒下降」等結論、沒有替代觀測或故障證據的刪除提案。

本專案的[測試成本案例](test-selection-case-study.md) 記錄實際篩選、Step 候選被最終檢查拒絕的原因，以及主 Agent 審查後的部分採用，分開呈現品質證據與耗時。
